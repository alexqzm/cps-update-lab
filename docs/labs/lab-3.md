# ЛР-3. Компрометация поставщика: похищенные ключи и сборочная среда

**Сценарии:** A2, A3, A3b. **Продолжительность:** 4 академических часа.

## Цель

Показать, почему подпись поставщика не отличает подлинный выпуск от вредоносного, если нарушитель
внутри цепочки поставщика, и какие свидетельства графа доказательств такую атаку опровергают.
Разобрать роль обязательных стадий (вето) и роль весов и порога, когда свидетельство не
опровергнуто, а просто отсутствует.

## Связь с реальными атаками

- [Stuxnet (2010)](https://github.com/alexqzm/cps-supply-chain-atlas/blob/main/data/records/stuxnet-2010.yaml):
  драйверы были подписаны скомпрометированными сертификатами Realtek и JMicron;
- [ShadowHammer (2019)](https://github.com/alexqzm/cps-supply-chain-atlas/blob/main/data/records/shadowhammer-2019.yaml):
  троянизированная утилита ASUS Live Update с действительными сертификатами ASUS
  распространялась с официальных серверов обновлений;
- [SolarWinds Orion (2020)](https://github.com/alexqzm/cps-supply-chain-atlas/blob/main/data/records/solarwinds-2020.yaml):
  программа SUNSPOT на сборочном сервере на время сборки подменяла исходный файл версией с
  бэкдором; обновления имели подпись SolarWinds;
- [X_TRADER и 3CX (2023)](https://github.com/alexqzm/cps-supply-chain-atlas/blob/main/data/records/xtrader-3cx-2023.yaml):
  нарушитель дошёл до сборочных сред 3CX, с сайта распространялась троянизированная версия;
- [TanStack (2026)](https://github.com/alexqzm/cps-supply-chain-atlas/blob/main/data/records/tanstack-2026.yaml):
  отравленный кэш CI привёл к публикации пакетов с вредоносным кодом и действительной
  аттестацией происхождения.

## Теория

**A2 — похищенные ключи.** У нарушителя ключи подписи пакета (cosign, роль vendor) и образа
(vendor_boot), но нет ключей сборочного агента, хранилища, рецензента и OpenPGP-ключа тегов
поставщика. Он собирает вредоносный образ с меткой версии 1.1.0 у себя, подписывает пакет и
образ похищенными ключами, а аттестации и тег — своими.

**A3 — заражённая сборочная среда.** Исходный код, тег, рецензирование и испытания подлинные.
Сборочный агент поставщика во время сборки подменяет программу. Все подписи сборочного конвейера
действительны: их ставит тот же заражённый агент. Расходится только контрольная пересборка той же
ревизии независимым сборщиком (s24).

**A3b** — то же без независимой пересборки. Опровергнутых свидетельств нет, но s24 не
предъявлено.

Гейт принимает решение по порядку: не предъявлено обязательное s22 или s42 — запрос; опровергнуто
свидетельство обязательной стадии (сборка, пакет) — отказ по вето; верхняя граница индекса R_P^max
ниже θ — отказ; иначе допуск или ручное рассмотрение.

## Ход работы

1. **Похищенные ключи: отчёт гейта.** Выполните `./lab.sh cli gate report tank-1.1.0-stolen-key`.
   Выпишите опровергнутые (F) и непредъявленные (N) свидетельства. Какие из них дают вето?

2. **Что видит проверка подписи.** В оболочке стенда (`./lab.sh shell`):

   ```bash
   S=/lab/vendor/releases/tank-1.1.0-stolen-key
   cosign verify-blob --key /lab/gate/keys/vendor.pub --insecure-ignore-tlog=true \
     --bundle $S/package/tank-controller-1.1.0.img.sigstore.json $S/package/tank-controller-1.1.0.img
   head -6 $S/source/tag_object
   cosign verify-blob-attestation --key /lab/gate/keys/builder.pub --insecure-ignore-tlog=true \
     --type https://slsa.dev/provenance/v1 --signature $S/build/provenance.intoto.json \
     $S/build/tank-controller-1.1.0.img
   ```

   Объясните результат каждой команды.

3. **Похищенные ключи на контроллере.** Выполните `./lab.sh scenario A2 1` и
   `./lab.sh scenario A2 2`. Запишите исходы.

4. **Заражённая сборка: отчёт гейта.** Выполните `./lab.sh cli gate report tank-1.1.0-compromised-build`.
   Какое единственное свидетельство опровергнуто? Сравните результаты двух пересборок:

   ```bash
   C=/lab/vendor/releases/tank-1.1.0-compromised-build
   for f in repro rebuild-independent; do
     python3 -c "import json,base64,sys; p=json.loads(base64.b64decode(json.load(open(sys.argv[1]))['payload']))['predicate']; print(sys.argv[1].split('/')[-1], p['builder']['id'], p['result'], p['rebuilt']['sha256'][:16], p['candidate']['sha256'][:16])" $C/build/$f.intoto.json
   done
   ```

   Почему пересборка самим сборщиком (s23) подтверждается?

5. **Заражённая сборка на контроллере.** Выполните `./lab.sh scenario A3 1` и
   `./lab.sh scenario A3 2`.

6. **Без независимой пересборки.** Выполните
   `./lab.sh cli gate report tank-1.1.0-compromised-build-norebuild`. Запишите G_P, B_P,
   R_P^min, R_P^max и решение. Почему отказ не по вето? Как изменилось бы решение при θ = 0,85?

7. **Испытания.** В отчётах шагов 4 и 6 свидетельство s43 (испытания) подтверждено. Объясните
   почему, сравнив программу из исходного кода (`./lab.sh cli image show tank-1.1.0`) и программу
   в выпуске (`./lab.sh cli image show tank-1.1.0-compromised-build`).

## Ожидаемые результаты

| Выпуск | Решение гейта | R_P^min … R_P^max | Ключевые свидетельства |
|---|---|---|---|
| tank-1.1.0-stolen-key | отказ (вето) | 0,000 … 0,450 | s11, s14, s21, s22, s41 — F; s12, s13, s23, s24, s31, s32, s43 — N |
| tank-1.1.0-compromised-build | отказ (вето) | 0,180 … 0,540 | s24 — F |
| tank-1.1.0-compromised-build-norebuild | отказ | 0,828 … 0,864 | s24 — N |

На контроллере: A2, A3 и A3b на L0 и L1 — принято, перелив; на L2 — отказ `NO_RECEIPT`, процесс в
норме.

   происхождения была действительной.
