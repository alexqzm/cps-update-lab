# ЛР-6. Выпускной архив не совпадает с тегом

**Сценарий:** A7. **Продолжительность:** 2 академических часа.

## Цель

Разобрать атаку, при которой подписанный исходный код в репозитории подлинный, а образ собран из
выпускного архива, содержимое которого с тегом не совпадает. Понять, какие свидетельства
связывают образ с подписанным исходным кодом и почему подпись поставщика здесь ничего не
доказывает.

## Связь с реальными атаками

[xz-utils 5.6.0 и 5.6.1 (2024)](https://github.com/alexqzm/cps-supply-chain-atlas/blob/main/data/records/xz-utils-2024.yaml):
выпускные архивы содержали бэкдор, часть которого была только в архивах: изменённого файла
`m4/build-to-host.m4` в git не было. Архивы создал и подписал сопровождающий: подпись
подтверждала автора выпуска, но не соответствие архива подписанному исходному коду.

## Теория

В сценарии процесс выпуска поставщика собирает образ не из тега, а из выпускного архива. В архив
добавлен файл «заводских уставок» `build-aux/tank-controller.defaults.json`, которого нет в git;
сборка применяет его поверх программы. Тег, коммит, рецензирование и испытания относятся к
подлинному исходному коду, подписи поставщика действительны.

Свидетельства стадии сборки привязывают образ к исходному коду: шаг сборки (s21) и
аттестация происхождения (s22) называют вход сборки, а пересборки (s23, s24) показывают, что из
ожидаемого коммита получается тот же образ. Здесь вход сборки — архив, а не коммит из тега, и
пересборка из тега даёт другой образ.

Отдельное свидетельство «выпускной архив соответствует подписанному тегу» проверяет инструмент
[source-match](https://github.com/alexqzm/source-match): он сравнивает архив с деревом тега
пофайлово. Инструмент установлен в образ стенда.

## Подготовка

```bash
./lab.sh up
./lab.sh cli release list
```

## Ход работы

1. **Отчёт гейта.** Выполните `./lab.sh cli gate report tank-1.1.0-from-archive`. Выпишите
   опровергнутые свидетельства и причины.

2. **Архив и тег.** В оболочке стенда (`./lab.sh shell`) сравните состав архива и тега:

   ```bash
   A=/lab/vendor/releases/tank-1.1.0-from-archive
   tar -tzf $A/source/tank-controller-1.1.0.tar.gz | grep -v '/$' | sed 's|^tank-controller-1.1.0/||' | sort > /tmp/archive.txt
   git -C /lab/vendor/src ls-tree -r --name-only tank-controller/v1.1.0 | sort > /tmp/tag.txt
   diff /tmp/tag.txt /tmp/archive.txt
   tar -xzOf $A/source/tank-controller-1.1.0.tar.gz tank-controller-1.1.0/build-aux/tank-controller.defaults.json
   ```

3. **Вход сборки в аттестации.** Там же извлеките параметры сборки из аттестации происхождения:

   ```bash
   python3 -c "import json,base64,sys; p=json.loads(base64.b64decode(json.load(open(sys.argv[1]))['payload']))['predicate']; print(json.dumps(p['buildDefinition']['externalParameters'], ensure_ascii=False, indent=1))" $A/build/provenance.intoto.json
   ```

   Сравните с тем же полем выпуска tank-1.1.0 (`/lab/vendor/releases/tank-1.1.0/...`).

4. **Проверка source-match.** Там же:

   ```bash
   source-match check --repo /lab/vendor/src --tag tank-controller/v1.1.0 \
     --archive $A/source/tank-controller-1.1.0.tar.gz --gpg-key /lab/gate/keys/tag_signers.asc \
     --markdown /tmp/source-match.md
   echo "код возврата $?"; cat /tmp/source-match.md
   ```

5. **Программа в образе.** Выйдите из оболочки и сравните программы:
   `./lab.sh cli image show tank-1.1.0` и `./lab.sh cli image show tank-1.1.0-from-archive`.

6. **Контроллер.** Выполните `./lab.sh scenario A7 1` и `./lab.sh scenario A7 2`.

## Контрольные вопросы

1. Подпись поставщика на пакете действительна, тег подписан, испытания пройдены. Почему этого
   недостаточно?
2. Какие поля аттестации происхождения позволяют гейту увидеть, что сборка шла не из тега?
3. Почему в xz-utils проверка контрольной суммы архива при сборке не помогла бы?
4. Какие файлы в выпускных архивах законно отличаются от тега (сгенерированные при выпуске) и
   как с ними быть, чтобы проверка соответствия не теряла смысла?
5. Какие свидетельства опровергли бы атаку на xz, если бы нарушитель внёс изменения и в git?
