# ЛР-1. Штатное обновление: свидетельства, решение гейта, квитанция

**Сценарий:** N1. **Продолжительность:** 2 академических часа.

## Цель

Разобраться, из чего складывается решение о допуске обновления по методу SCII: какие
свидетельства собирает поставщик на каждой стадии цепочки, как гейт вычисляет их состояния и
индекс доверия, что содержит квитанция допуска и как контроллер проверяет её перед установкой.

## Теория

Цепочка выпуска ПО представлена графом стадий: источник (v1) → сборка (v2) → хранилище
артефактов (v3) → пакет обновления (v4) → устройство (v5). На каждой стадии есть свидетельства —
подписанные утверждения о том, что произошло: подпись коммита, аттестация происхождения SLSA,
результат независимой пересборки, подпись пакета и т. д. Гейт присваивает каждому свидетельству
состояние: **P** — подтверждено, **F** — опровергнуто (подпись не сходится, дайджест не
совпадает), **N** — не предъявлено.

Из состояний и весов гейт вычисляет индекс доверия R_P (с интервалом R_P^min…R_P^max, который
учитывает неточность весов) и принимает решение: допуск, ручное рассмотрение, запрос
свидетельств или отказ. Стадии «сборка» и «пакет обновления» обязательны: опровергнутое
свидетельство в них — вето, отказ независимо от индекса.

При допуске гейт выдаёт квитанцию SCII-R v1 — 244 байта, подписанные ключом гейта. Квитанция
привязывает допуск к классу и экземпляру устройства, к номеру версии (svn), к длине и дайджесту
образа и к политике. Контроллер уровня L2 проверяет её агентом scii-agent до записи образа во
флеш-память.

Подробно — в [`docs/architecture.md`](../architecture.md).

## Подготовка

```bash
./lab.sh up        # если стенд ещё не запущен
```

Откройте HMI: http://127.0.0.1:8081. Контроллер работает с программой ТК-1 1.0.0, уровень
защиты L2.

## Ход работы

1. **Выпуски и решения.** Выполните `./lab.sh cli release list`. Запишите, какие выпуски гейт
   допустил и для каких выдал квитанцию.

2. **Комплект свидетельств.** Выполните `./lab.sh cli release show tank-1.1.0`. Сопоставьте
   ключи раздела `evidence` (s11…s53) с файлами комплекта. Откройте оболочку стенда
   (`./lab.sh shell`) и просмотрите каталог выпуска:

   ```bash
   R=/lab/vendor/releases/tank-1.1.0
   find $R -type f | sort
   ```

3. **Проверка подписей вручную.** В оболочке стенда проверьте те же подписи, что проверяет гейт:

   ```bash
   export GNUPGHOME=$(mktemp -d)
   gpg --import /lab/gate/keys/tag_signers.asc
   git -C /lab/vendor/src log --oneline --decorate
   git -C /lab/vendor/src verify-tag tank-controller/v1.1.0                 # s14
   git -C /lab/vendor/src verify-commit 'tank-controller/v1.1.0^{commit}'   # s11
   cosign verify-blob --key /lab/gate/keys/vendor.pub --insecure-ignore-tlog=true \
     --bundle $R/package/tank-controller-1.1.0.img.sigstore.json $R/package/tank-controller-1.1.0.img   # s42
   cosign verify-blob-attestation --key /lab/gate/keys/builder.pub --insecure-ignore-tlog=true \
     --type https://slsa.dev/provenance/v1 --signature $R/build/provenance.intoto.json \
     $R/build/tank-controller-1.1.0.img                                     # s22
   ```

   Извлеките утверждение из аттестации происхождения и найдите в нём коммит, идентификатор
   сборщика и SHA-256 тулчейна:

   ```bash
   python3 -c "import json,base64,sys; e=json.load(open(sys.argv[1])); print(json.dumps(json.loads(base64.b64decode(e['payload'])), ensure_ascii=False, indent=1))" $R/build/provenance.intoto.json
   ```

4. **Решение гейта.** Выполните `./lab.sh cli gate report tank-1.1.0`. Запишите состояния
   свидетельств, R_P^min, R_P^max, порог θ и решение. Объясните, почему s54 имеет состояние N и
   почему решение всё равно «допуск».

5. **Квитанция.** Выполните `./lab.sh cli receipt show tank-1.1.0`. Сверьте:
   - `image_digest` — с SHA-256 образа из `release list`;
   - `policy_digest` — с `sha256sum /lab/gate/policy.json` в оболочке стенда;
   - `svn` — с версией 1.1.0 по формуле svn = major·2³² + minor·2¹⁶ + patch·2⁸ + 255.

6. **Проверка квитанции агентом.** В оболочке стенда запустите scii-agent с параметрами
   контроллера:

   ```bash
   cfg() { python3 -c "import json,sys; print(json.load(open('/lab/devices/plc-1/config.json'))[sys.argv[1]])" "$1"; }
   RUN=$(ls -d /lab/gate/runs/*-tank-1.1.0)
   agent() { scii-agent --image $R/package/tank-controller-1.1.0.img --receipt $RUN/receipt.scr \
     --pk $(cfg gate_pk) --suite 1 --epoch-lo 1 --epoch-hi 4294967295 --policy-digest $(cfg policy_digest) \
     --min-epoch 1 --instance $(cfg instance) "$@"; echo "код выхода $?"; }
   agent --board-id 7001 --installed-svn 0x1000000ff     # контроллер ТК-1 с версией 1.0.0
   agent --board-id 7002 --installed-svn 0x1000000ff     # другой класс устройства
   agent --board-id 7001 --installed-svn 0x1000200ff     # на устройстве уже 1.2.0
   ```

   Запишите ответ агента в каждом случае.

7. **Штатное обновление.** Выйдите из оболочки и выполните `./lab.sh scenario N1 2`. Убедитесь в
   HMI, что контроллер работает с версией 1.1.0, а в журнале появилась запись об установке.
   Выполните `./lab.sh monitor`: тревог быть не должно.

## Контрольные вопросы

1. Чем свидетельство в состоянии N отличается от свидетельства в состоянии F? Как каждое из них
   влияет на решение гейта?
2. Почему гейт проверяет подпись тега ключом из своей политики, а не ключом, приложенным к
   выпуску?
3. Какие поля квитанции защищают от установки подлинного образа не на то устройство и не в ту
   версию?
4. Зачем в квитанции дайджест политики и что произойдёт, если гейт сменит политику, а контроллер —
   нет?
5. Порог θ на стенде равен индексу эталонного выпуска. Какие последствия у такого выбора и как
   выбирать порог на практике?
